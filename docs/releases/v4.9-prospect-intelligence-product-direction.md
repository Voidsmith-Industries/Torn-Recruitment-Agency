# Recruitment Agency v4.9 — Prospect Intelligence Product Direction

Status: APPROVED / PLANNED  
Approved by: George  
Date: 2026-10-06  
Implementation status: Not yet implemented

## Purpose

v4.9 evolves Torn Recruitment Agency from a primarily search-and-filter workflow into a broader prospect-intelligence workspace while preserving the existing browser-first, local-first and manual-contact safety model.

The design is competitor-informed, including useful presentation and discovery ideas observed in TornCrew, but implementation must remain an original Voidsmith design built around Recruitment Agency's existing architecture and data boundaries.

## Locked product decisions

### 0. Single-context Company / Faction mode selector

Recruitment Agency is a userscript and must manage one recruitment context at a time.

A persistent dropdown in the top-left of the application shell, near the Recruitment Agency title, selects the active workspace:

- Company
- Faction

The left navigation is context-sensitive and must show only routes relevant to the selected workspace. The interface must not render separate Company and Faction navigation trees at the same time.

The Player Card is also context-sensitive. In Company mode it shows company-relevant status, fit and actions only. In Faction mode it shows faction-relevant status, fit and actions only. Shared public Player Intelligence may still back both views, but private workflow state remains isolated.

Changing the workspace must preserve browser-local preferences and must not merge Company and Faction private workflow state.

### 1. Results presentation

Expanded Table is the default results layout.

Company Recruitment results should expose useful decision data directly in the row, including where legitimately available:

- Player
- Level
- Age
- MAN
- INT
- END
- Drug-use signal
- 30-day activity
- Activity streak
- Employment/current company
- Last action
- Recruitment Fit
- Contacted state

Faction Recruitment should use the same dense-results principle with faction-relevant intelligence such as:

- Player
- Level
- Age
- Net worth
- Drug-use signal
- 30-day activity
- Battle-stat signal where legitimately available
- Activity streak
- Recent Xanax signal where legitimately available
- Current faction
- Last action
- Recruitment Fit
- Contacted state

Every meaningful comparable numeric or temporal column should be sortable. Unknown values remain Unknown / em dash and must never be silently converted to zero or fabricated.

### 2. Compact Results option

Settings must allow the recruiter to switch from Expanded Table to Compact Table.

Compact Table keeps only core fields needed for fast recruitment, such as player identity, primary recruitment stats, last action, fit and contact action.

The hidden intelligence remains available through Player Card.

Expanded Table remains the default.

### 3. Player Card

Clicking a player name opens a Player Card without navigating away from Results.

The card should present the candidate's available intelligence in one place, including:

- Identity
- Level / age
- Recruitment-relevant stats
- Activity
- Current employment/faction state
- Recruitment source/provenance
- First seen / last observed / last enriched
- Contact state
- Notes
- History
- Fit-score explanation
- Intelligence freshness/confidence

Company and Faction cards adapt to their respective domains while reading from the shared Player Intelligence identity where appropriate.

### 4. Pop-out and pin

Player Card must be able to detach into a persistent side panel.

Expected behavior:

- Pop Out keeps the candidate visible while browsing Results.
- Selecting another player updates an unpinned panel.
- Pin prevents the panel from changing when another candidate is selected.
- The design should permit a future extension to limited side-by-side pinned comparison without requiring a separate rewrite.

### 5. Results settings

Settings should expose at minimum:

- Results layout: Expanded Table / Compact Table
- Open Player Card when player name is clicked
- Allow Player Card to pop out as side panel
- Remember open panel between Recruitment Agency pages
- Optional automatic card opening on row selection

These preferences remain browser-local.

### 6. Discovery sources

v4.9 should treat candidate discovery as a multi-source pipeline:

1. Recruitment forums / Job Seekers: people explicitly looking.
2. Torn user search: targeted public player discovery.
3. Public work-stat leaderboard discovery: passive prospects.
4. Existing local Player Intelligence: previously discovered candidates and reactivation opportunities.

No single source replaces the others.

### 7. Recruitment Fit Score

Recruitment Fit must be explainable rather than an opaque magic number.

The UI should show both:

- Fit score, e.g. 87 / 100
- Confidence: High / Medium / Low

The score may include configurable positive and negative contributions such as:

- Work-stat match
- Role requirement match
- Activity
- Employment state
- Explicit forum job-seeking signal
- Recent contact penalties
- Data freshness/confidence

The user must be able to inspect why a score was produced.

### 8. Role profiles and saved searches

Recruiters should be able to save named search profiles for recurring needs.

A profile may include:

- Company type / faction context
- Position or role
- Minimum MAN / INT / END
- Preferred stat weighting
- Activity threshold
- Employment/faction requirement
- Level range
- Discovery sources
- Fit weighting
- Exclusion window for recently contacted candidates

Saved profiles must remain local unless a future separately approved architecture introduces sync.

### 9. Provenance and history

Every candidate should retain visible provenance and history.

Examples:

- Company Recruitment Forum
- Faction Recruitment Forum
- Torn User Search
- Work-stat leaderboard
- Previously known local intelligence

The UI should expose first discovered, last observed and last enriched timestamps where known.

The system should distinguish useful recruitment states such as:

- Active Lead
- Passive Prospect
- Known Candidate
- Reactivation Candidate

### 10. Watchlist / Talent Pool integration

Watchlist-style functionality should use or extend Recruitment Agency's existing Talent Pool / candidate-history model rather than create a duplicate isolated store.

### 11. Staged enrichment and API efficiency

Cheap discovery and local filtering should happen before expensive enrichment.

Opening a Player Card must not automatically refetch everything.

The card reads existing Player Intelligence immediately. Missing or stale data may expose an explicit Refresh Intelligence action routed through the existing API scheduler and pacing controls.

### 12. Contact safety remains unchanged

v4.9 must preserve the existing safe-contact model:

- Fresh official Torn membership checks where required
- Separate Company and Faction message contexts
- Prepared private-chat text
- Final Send remains manual
- Do Not Contact protections remain in force
- No automatic send, synthetic Enter submission or hidden contact-state mutation merely because a draft was prepared

### 13. Company/Faction isolation remains unchanged

One Torn player ID maps to one shared public Player Intelligence identity, but Company and Faction private workflow state remain isolated.

Do not merge private notes, stages, campaigns, follow-ups, waivers or workflow history across domains unless a separately approved design explicitly changes that rule.

### 14. Data integrity

Recruitment Agency must never invent MAN, INT, END, battle stats, drug-use values or other player facts that Torn does not expose or that are not legitimately known from an approved source.

Unknown stays unknown.

All enriched facts should preserve source/provenance and freshness where practical.

## UX principle

The Results row is the main working surface.

The recruiter should be able to:

Search → compare → sort → inspect → contact

without repeatedly navigating into separate pages just to decide whether a candidate is worth approaching.

Advanced intelligence remains available, but it should not obstruct the default recruiting workflow.

## Out of scope for the v4.9 design lock

This document does not authorize:

- Runtime implementation
- Database/schema changes
- Public release
- Website/distribution updates
- Production/VPS changes
- Automated messaging
- Server-side centralization of normal Recruitment Agency operation
- Monetization/paywall changes
- Copying proprietary TornCrew implementation details

Implementation requires a separate bounded Task ID, current repository inspection, tests and normal release verification.
